# spec-code-review — 代码评审

## 定位

独立的任务式技能，不依赖已有议题。用户通过 `/spec-code-review {描述}` 发起，AI 从 git 变更开始分析，检视新增代码与设计文档的一致性。

**适用时机**：开发完成但尚有关键变更未确认时；提交 PR 前做一轮文档一致性检查。

**不适用**：纯粹的技术债清理或重构（无需比照设计文档）；尚未开发完成。

---

## 流程总览

```
Phase 1 — 收集（AI 自动完成）
  用户描述 → 获取锚点 → git log/diff → 扫描关联文档

Phase 2 — 展示（AI 汇总）
  AI 标注可能偏差的热点 → 用户圈定深入评审的范围

Phase 3 — 确认（人主导）
  AI 并排展示代码 vs 文档 → 用户判断差异性质 → 收集判定

Phase 4 — 收尾
  更新评审锚点 → 汇总输出 → 写入报告 → 引导后续动作
```

---

## Phase 1：收集

### Step 1-1：解析用户描述

从 `/spec-code-review {描述}` 中提取：
- **关注范围**：用户指定要评审的文件、模块或功能点（如「评审 auth 模块的改动」）
- 如描述为空或无明确指向，则评审锚点之后的所有新增提交

### Step 1-2：获取评审锚点

调 `get_git_history()` 获取上次评审的 commit hash。

两种情况：

```
① 有锚点（hash 非空）
   后续用 git log <hash>..HEAD --oneline 取增量

② 无锚点（首次评审）
   AI 提示用户并询问起点：
   > 尚无历史评审记录，请指定起始 commit
   > （如 git log --oneline 中的某个 hash），
   > 或输入 first 从首个 commit 开始。
```

如果用户描述中明确指向某个范围（如「从 v1.0 tag 开始评审」），优先使用用户指定的起点。

### Step 1-3：获取 git 变更

```bash
# 提交清单
git log <锚点>..HEAD --oneline

# 变更文件概览
git diff --stat <锚点>..HEAD

# 完整 diff
git diff <锚点>..HEAD
```

如果用户描述中指定了关注范围，追加路径过滤缩小结果：
```bash
git log <锚点>..HEAD --oneline -- <路径1> <路径2>
git diff <锚点>..HEAD -- <路径>
```

展示提交清单给用户确认是否覆盖全部文件，或需进一步缩小。

### Step 1-4：读取相关设计文档

调 `doc_structure()` 获取所有文档路径和 section 标题。

根据变更文件的路径语义和用户描述中的关注点，匹配相关文档：
- 如 `auth.py` → 匹配 `architecture.md` 中「认证」相关段落、`technical-constraints.md` 中「安全」相关段落
- 如用户描述提到「接口变更」→ 匹配 `inter-module-contracts.md`
- 对匹配到的文档调 `read_doc(path)` 获取完整内容

> 匹配规则是启发式的 — 按文件名、section 标题、用户描述三者之间的语义关联，不做精确映射。

---

## Phase 2：展示

### Step 2-1：AI 扫描热点

AI 基于 diff 文本和设计文档，做 best-effort 扫描，标注"可能存在偏差"的热点区域。输出格式：

```
📋 本次评审概况

用户关注: {从描述提取的关注范围}

变更文件清单（共 N 个）:
  - src/auth/token.py   (15 行新增)
  - src/api/handlers.py (8 行新增)

关联设计文档:
  - architecture.md → §认证流程、§token 生命周期
  - technical-constraints.md → §安全约束

🔍 AI 标注的热点区域（仅供参考，需人工确认）:
  ① token.py:14-18 — 过期时间从 30min→60min，
     与 architecture.md §认证流程「token 有效期 30 分钟」不一致
  ② handlers.py:22-25 — 新增角色校验逻辑，
     文档中无此约束描述
```

对每个热点标注风险等级：
- 🔴 **高** — 行为变更可能影响安全、稳定性、外部接口
- 🟡 **中** — 设计偏差，需确认是设计变更还是实现失误
- 🟢 **低** — 文档滞后或次要差异

**注意**：AI 标注仅为辅助，标注可能不准确或有遗漏。判定权在用户。

### Step 2-2：用户选择

请用户回答：

> 以上 AI 标注的热点区域中，哪些需要深入比对？
> 是否有未标注的区域需要 AI 辅助查看？

用户选择后进入 Phase 3。

---

## Phase 3：确认

对用户选中的每个热点区域，逐一确认：

### Step 3-1：并排展示

对于每个待确认点，AI 并排展示「文档原文」vs「代码原文」：

```
📄 文档 — architecture.md §认证流程
> token 有效期 30 分钟，过期后需刷新。

💻 代码 — src/auth/token.py:14-18
> TOKEN_TTL = 60  # 改为 60 分钟

差异要点：...（AI 列出关键表/字段层面的对比）
```

### Step 3-2：引导用户判定

```
这是一个什么性质的差异？

A. **设计变更** — 代码有意偏离原设计，需更新文档记录新决策
B. **实现偏差** — 代码实现有误，应改回与文档一致
C. **文档过时** — 文档未及时更新，需更新文档以反映实际实现
D. **误报** — 代码与文档一致，AI 判断有误
```

### Step 3-3：记录判定

将用户判定暂存在内存中（一个列表），格式：

```
[差异简述] token 过期时间 30min→60min
[性质]     设计变更
[风险等级]  🟡 中
[后续动作]  更新 architecture.md §认证流程，记录新的过期时间及理由
```

### Step 3-4：逐条处理

重复 Step 3-1~3-3 直到所有选中的热点区域处理完毕。

---

## Phase 4：收尾

### Step 4-1：更新评审锚点

获取 HEAD 完整 hash：

```bash
git rev-parse HEAD
```

调 `add_git_history(commit_hash)` 保存锚点。

### Step 4-2：汇总输出

按以下 Markdown 模板组织评审报告（**所有段落必须包含**）：

```markdown
# Code Review Report — {简短标题}

> **评审日期**: {YYYY-MM-DD}
> **评审范围**: {锚点}..{HEAD}
> **用户关注**: {从描述提取的关注范围}

## 基本信息

| 项目 | 内容 |
|------|------|
| 评审日期 | {YYYY-MM-DD} |
| 评审 Git 范围 | {锚点}..{HEAD} |
| 关注范围 | {用户描述} |
| 变更文件数 | {N} 个 |

### 变更文件清单

| 文件 | 类型 | 规模 |
|------|------|------|
| path/to/file1.py | 修改 | XX 行变更 |
| path/to/file2.py | 新建 | XX 行全新 |

### 关联设计文档

- {doc-path-1} → §{相关段落}
- {doc-path-2} → §{相关段落}

## 评审热点

AI 标注的 N 个潜在偏差区域：

| # | 差异简述 | 文档位置 | 代码位置 | 风险等级 |
|---|---------|---------|---------|---------|
| ① | {简述} | {doc} §{段落} | {file}:{line} | 🔴/🟡/🟢 |
| ② | {简述} | ... | ... | 🔴/🟡/🟢 |

## 深入确认项

用户逐条确认后的差异判定：

| # | 差异 | 性质 | 后续动作 |
|---|------|------|---------|
| ③-a | {差异简述} | 设计变更/实现偏差/文档过时 | {具体后续动作} |
| ③-b | {差异简述} | ... | ... |

## 未深入比对项

未进行逐条比对的热点：

| # | 差异 | 风险等级 | 简要说明 |
|---|------|---------|---------|
| ① | {简述} | 🔴/🟡/🟢 | {一句话说明} |
| ② | {简述} | ... | ... |

## 后续动作

基于评审结果的可选后续步骤：

1. ...
2. ...
```

### Step 4-3：写入评审报告

将 Step 4-2 生成的 Markdown 报告调 `write_review_report(report_markdown)` 写入 `ReviewSpec/`。

> 文件自动命名为 `code-review-{YYYYMMDD-HHMMSS}.md`。
> 服务端校验必填段落（`# ` 标题、`## 基本信息`、`## 评审热点`），
> 缺失时返回 warning 但仍写入文件。

### Step 4-4：引导后续动作

> ✅ 代码评审完成。报告已写入 ReviewSpec/{filename}，评审锚点已更新。
>
> 🔗 如需将差异记入会议议题追踪，可调 spec-start 开启新议题。
> 📄 如需直接更新文档，可用 update_section() 或 add_section()。
