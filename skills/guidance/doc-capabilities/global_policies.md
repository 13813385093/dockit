# 能力说明：global_policies（global-policies.md）

> 指南：§3.1.2 / 类型 T-04（维护索引，供指南更新时同步本文件；AI 无需访问）
> 层级：Level 0（top）· `module: project-charter` · 必选 · 编写顺序第 4

## 定位

影响 ≥2 个模块的统一策略：认证、日志、错误码、一致性、命名、依赖管理等。同一件事在两个以上模块出现时在此统一定义，避免各自为政。策略是**活文档**，随项目演进持续更新。

## 段落结构（每个策略独立一个章节）

每个策略必须包含 4 个要素：

```
## [策略名称]

**影响的模块**：[至少 2 个受影响的模块]

[策略定义：全局统一的做法或规范（表格/列表）]

**为何需要统一**：[不统一会出什么问题]
```

- 正例（§安全与认证）：认证机制 OAuth2 / JWT / 证书；授权模型 RBAC / ABAC；传输加密 TLS；密钥轮换策略。为何统一：各模块各自实现认证会导致安全漏洞，用户需要多套凭证，审计无法追溯。
- 正例（§命名约定）：模块名 kebab-case（如 data-storage）、类名 PascalCase、函数 snake_case（Python）/camelCase（JS/TS）。为何统一：命名不一致时搜索效率低下，AI 生成的代码难以遵循统一风格。

## 行文规则

**必须**
- 判断是否写入本文档：影响 **≥2 个模块** → 写这里；不统一后果是系统级问题（安全漏洞、无法运维、数据不一致）→ 写这里
- 各模块必须遵守的规则用 `[MUST]` / `[SHOULD]` 标记并编号（`C-1xx` / `S-1xx`，文档内唯一）
- 每个策略写明「为何需要统一」——帮助新成员理解权衡

**禁止**
- ❌ 只影响单个模块的策略 → 写该模块自己的文档
- ❌ 量化指标或门槛 → 归 `non_functional_constraints`（本文档管「怎么做」，它管「必须达到什么指标」）
- ❌ 模块内具体实现细节 → 归对应模块文档
