# 能力说明：global_policies（global-policies.md）

> 指南：§3.1.2 / 类型 T-04（维护索引，供指南更新时同步本文件；AI 无需访问）
> 层级：Level 0（top）· `module: project-charter` · 必选 · 编写顺序第 4 · 位于 `ProjectSpec/` 根（平铺，不建子目录）

## 定位

影响 ≥2 个模块的统一策略：认证、日志、错误码、一致性、命名、依赖管理等。同一件事在两个以上模块出现时在此统一定义，避免各自为政。策略是**活文档**，随项目演进持续更新。不写只影响单模块的策略（→ 归该模块文档）与量化门槛（→ 归 `non_functional_constraints`）。

## 段落结构（记录式：每条记录含固定要素，顺序固定，条数不限）

每个策略必须包含 4 个要素（与指南 §3.1.2 的 global-policies 模板逐字一致）：

```
## [策略名称]

### 涉及范围
**影响的模块**：[列出至少 2 个受影响的模块]

### 策略定义
[全局统一的做法或规范]

### 各模块必须遵守的规则
- [MUST] C-101 [规则1]
- [SHOULD] S-101 [规则2]

### 为何需要统一
[不统一会出什么问题，帮助新成员理解权衡]
```

- 格式：每条记录 = `## [策略名称]` 标题 + `### 涉及范围`（**影响的模块**）/ `### 策略定义` / `### 各模块必须遵守的规则`（`- [MUST] C-101 <规则>` 列表）/ `### 为何需要统一`，顺序固定，条数不限
- 正例：认证机制 OAuth2 / JWT / 证书；授权模型 RBAC / ABAC；传输加密 TLS；密钥轮换策略。为何统一：各模块各自实现认证会导致安全漏洞，用户需要多套凭证，审计无法追溯。（§安全与认证）
- 正例：统一结构化日志（JSON；字段 ts/level/trace_id/module/msg），跨模块调用必须透传 trace_id。（§可观测性）
- 正例：跨模块写操作一律最终一致，禁止跨模块事务；补偿逻辑必须可重放。（§数据一致性）
- 正例：错误码统一 `<域>.<类别>.<编号>`（如 order.biz.1001）；对外接口不得泄漏内部异常堆栈。（§异常处理）
- 正例：审计日志留存 ≥ 180 天，含操作者、时间、对象、结果；个人信息字段入库前脱敏。（§合规与审计）
- 反例：各模块自行决定日志格式（有的 JSON、有的纯文本），导致集中检索与审计失效。（§合规与审计）
- 正例：语言版本统一 Python 3.11+；格式化 black、类型检查 mypy、lint ruff。（§代码规范）
- 正例：统一用 pnpm 并提交锁文件；新增依赖须通过许可证白名单检查。（§依赖管理）
- 正例：模块名 kebab-case（如 data-storage）、类名 PascalCase、函数 snake_case（Python）/camelCase（JS/TS）。为何统一：命名不一致时搜索效率低下，AI 生成的代码难以遵循统一风格。（§命名约定）

**主题归属（各策略主题与相邻文档的边界）**

- §架构模式：本文档定义**跨模块统一通信约定**（消息命名、幂等/投递语义、重试与死信）；**架构风格与中间件选型归 `technical_framework.md` §架构风格、§主要框架与中间件**；**单个接口的通信方式归 `inter_module_contract`**。
- §异常处理：本文档定义**系统级**错误码体系与统一降级/恢复策略；**单个外部系统的集成失败处理归 `integration.md` §错误处理与降级**。
- §代码规范：本文档定义**规范内容与统一做法**（语言版本、格式化、类型检查、工具链约定）；**覆盖率等量化门槛归 `non_functional_constraints.md` §编码规范**。
- §安全与认证、§合规与审计：合规的**落地机制**（审计日志格式、留存期、脱敏）归本文档；**是否必须符合某标准**归 `non_functional_constraints`。

## 行文规则

> 本节「禁止」＝ 指南 §3.1.2 中本文档的「约束」（写作边界）；指南中的「约束」不指 [MUST]/[SHOULD] 内容级标记。

**必须**
- 落笔格式：每个策略独立一个 `## [策略名称]` 记录，按 4 要素顺序填写（`### 涉及范围` / `### 策略定义` / `### 各模块必须遵守的规则` / `### 为何需要统一`）
- 判断是否写入本文档：影响 **≥2 个模块** → 写这里；不统一后果是系统级问题（安全漏洞、无法运维、数据不一致）→ 写这里
- 编号与命名：各模块必须遵守的规则用 `[MUST]` / `[SHOULD]` 标记并编号（`C-1xx` / `S-1xx`，文档内唯一）。编号在**本文档内唯一**；跨文档引用用完整形式（语法见指南 §3.5.5）：`<doc_type>@project-charter:C-101`（顶层）／`<doc_type>@<模块名>:C-101`（模块层）／`<doc_type>@<模块名>.<功能名>:C-101`（功能层）。
- 完备性：每个策略写明「为何需要统一」——帮助新成员理解权衡
- 与他文档的衔接：策略涉及量化门槛时只写做法，门槛数值以 `non_functional_constraints` 的编号为准并引用之

**禁止**
- ❌ 只影响单个模块的策略 → 写该模块自己的文档
- ❌ 量化指标或门槛 → 归 `non_functional_constraints`（本文档管「怎么做」，它管「必须达到什么指标」）
- ❌ 模块内具体实现细节 → 归对应模块文档
- ❌ 量化门槛（覆盖率数值等）→ `non_functional_constraints` §编码规范
- ❌ 法规/标准符合性要求 → `non_functional_constraints`
- ❌ 中间件/技术选型 → `technical_framework`
- ❌ 单个外部系统的集成失败处理 → `integration.md`
- ❌ 质量禁忌：模糊表述（「尽量统一」）、不可验证的做法、无来源的结论
