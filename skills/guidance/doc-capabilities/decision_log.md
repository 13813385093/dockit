# 能力说明：decision_log（decision-log.md）

> 指南：§3.3.2 / §3.3.3 / 类型 T-12（维护索引，供指南更新时同步本文件；AI 无需访问）
> 层级：Level 2（feature）· 必选 · 编写顺序第 12 · 位于 `module-<模块名>/features/<功能名>/`

## 定位

记录关键设计决策的背景、理由和替代方案分析（Why，左翼）。为未来评审和变更提供可追溯依据。**既有决策记录不可修改；结论变化时追加一条新决策记录，而非改写旧记录。**

## 承载的决议主题

| 决议主题 | 目标章节 |
|---------|---------|
| 技术/业务选型理由与权衡 | 新增一条决策记录 |
| 方案对比与评估 | 决策记录 §替代方案分析 |
| 结论变更（追加新记录） | 新增决策记录（不改写旧记录） |

## 段落结构（每条决策一个 `### 决策：<标题>` 记录，顺序固定）

```
### 决策：<决策标题>

**日期** / **决策者** / **状态**（已批准 / 待定 / 已废弃）

#### 问题描述
#### 业务Why
#### 技术Why
#### 替代方案分析
| 方案 | 优点 | 缺点 | 评估结果 |
#### 最终决策
```

- 正例（问题）：选择 GOOSE 还是 MMS 传输跳闸信号？
- 正例（业务Why）：GOOSE 满足 ≤4ms 的硬性延迟要求；符合 IEC 61850 标准对快速保护的要求。
- 正例（技术Why）：GOOSE 基于以太网组播无需 IP 路由；直接在数据链路层传输减少协议栈开销；支持报文重传机制确保可靠性。
- 正例（替代方案）：方案A MMS（延迟约 10-50ms 不满足实时性 → 不推荐）；方案B 自定义UDP（缺乏标准互操作性 → 不推荐）；方案C GOOSE（最优 → 推荐）。

## 行文规则

**必须**
- 只记录结论和理由（业务Why + 技术Why），替代方案给出评估结果（推荐/不推荐）
- 纪律：**追加不改写**——既有决策记录保持原样，结论变化时追加新记录
- 每条决策标注日期、决策者、状态

**禁止**
- ❌ 会议纪要或讨论过程
- ❌ 功能行为定义（触发、流程、约束）→ 归 `feature_design`
- ❌ 测试用例 → 归 `unit_test` / `acceptance_test`
