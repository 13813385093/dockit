# 能力说明：decision_log（decision-log.md）

> 指南：§3.3.2 / §3.3.3 / 类型 T-12（维护索引，供指南更新时同步本文件；AI 无需访问）
> 层级：Level 2（feature）· 必选 · 编写顺序第 12 · 位于 `module-<模块名>/features/<功能名>/`

## 定位

记录关键设计决策的背景、理由和替代方案分析（Why，左翼）。为未来评审和变更提供可追溯依据。**既有决策记录不可修改；结论变化时追加一条新决策记录，而非改写旧记录。** 不写功能行为定义（→ feature_design）与会议过程。

## 承载的决议主题

| 决议主题 | 落点（章节 / 新增记录） |
|---------|---------|
| 技术/业务选型理由与权衡 | 新增一条决策记录 |
| 方案对比与评估 | 决策记录 §替代方案分析 |
| 结论变更（追加新记录） | 新增决策记录（不改写旧记录） |

## 段落结构（记录式：每条记录含固定要素，顺序固定，条数不限）

```
## 决策：<决策标题>

**日期** / **决策者** / **状态**（已批准 / 待定 / 已废弃）

### 问题描述
### 业务Why
### 技术Why
### 替代方案分析
| 方案 | 优点 | 缺点 | 评估结果 |
### 最终决策
```

- 格式：每条记录 = `## 决策：<决策标题>` + 一行 `**日期** / **决策者** / **状态**` + `### 问题描述` / `### 业务Why` / `### 技术Why` / `### 替代方案分析`（含上表）/ `### 最终决策`
- 正例：选择 GOOSE 还是 MMS 传输跳闸信号？（问题描述）
- 正例：GOOSE 满足 ≤4ms 的硬性延迟要求；符合 IEC 61850 标准对快速保护的要求。（业务Why）
- 正例：GOOSE 基于以太网组播无需 IP 路由；直接在数据链路层传输减少协议栈开销；支持报文重传机制确保可靠性。（技术Why）
- 正例：方案A MMS（延迟约 10-50ms 不满足实时性 → 不推荐）；方案B 自定义UDP（缺乏标准互操作性 → 不推荐）；方案C GOOSE（最优 → 推荐）。（替代方案分析）

## 行文规则

> 本节「禁止」＝ 指南 §3.3.2 中本文档的「约束」（写作边界）；指南中的「约束」不指 [MUST]/[SHOULD] 内容级标记。

**必须**
- 只记录结论和理由（业务Why + 技术Why），替代方案给出评估结果（推荐/不推荐）
- 纪律：**追加不改写**——既有决策记录保持原样，结论变化时追加新记录
- 每条决策标注日期、决策者、状态
- 一次决策一条记录：以 `## 决策：<决策标题>` 起头（标题须自解释，如「支付回调采用异步消息而非同步 RPC」）；固定要素顺序为 问题描述 / 业务Why / 技术Why / 替代方案分析 / 最终决策
- 每条结论须给出来源与依据：为什么这么选、替代方案为什么不选
- 与他文档衔接：决策所依据的约束写在 `feature_design` §边界约束，验证落在 `unit_test` / `acceptance_test`，本文档只记理由与结论

**禁止**
- ❌ 会议纪要或讨论过程
- ❌ 功能行为定义（触发、流程、约束）→ 归 `feature_design`
- ❌ 测试用例 → 归 `unit_test` / `acceptance_test`
- ❌ 无来源的结论或未经评估的选项（如「这样更好」而无方案对比）
- 反例：把评审会各方发言原文与讨论过程抄进决策记录（会议过程不入 Spec，只记结论与理由）。
