# 能力说明：acceptance_test（acceptance-tests.md）

> 指南：§3.3.2 / §3.5.8 / 类型 T-14（维护索引，供指南更新时同步本文件；AI 无需访问）
> 层级：Level 2（feature）· 必选 · 编写顺序第 14 · 位于 `module-<模块名>/features/<功能名>/`

## 定位

以 BDD 风格 Gherkin 语法描述完整业务场景，验证功能是否符合业务预期。关注**业务符合性**（"做的是用户要的吗？"）。不写代码级验证（→ unit_test）与功能约束定义（→ feature_design）。

## 承载的决议主题

| 决议主题 | 落点（章节 / 新增记录） |
|---------|---------|
| 业务验收场景（正常/异常路径） | 新增 Gherkin 场景 |

## 段落结构（记录式：每条记录含固定要素，顺序固定，条数不限）

```gherkin
# language: zh-CN
功能: <功能名称>
  作为 <角色>
  我希望 <功能目标>
  以便 <业务价值>

  场景: <场景名>
    假设 <前置条件>
    当  <触发动作>
    那么 <预期结果1>
    并且 <预期结果2>
```

术语澄清：设计侧「**适用前提**」＝功能可执行时系统必须已处于的状态；测试侧 `Given 前置条件` / Gherkin `假设` ＝单个用例的初始输入状态，二者不同层次。

- 格式：每个场景 = `场景: <场景名>` + `假设` / `当` / `那么` / `并且`（多预期时重复「并且」）四类关键字行；所有场景写入同一文件，按顺序追加
- 正例：功能 电压异常跳闸保护 / 作为 电网调度员 / 我希望 系统在电压异常时快速跳闸 / 以便 保护设备安全。场景 电压过阈值触发跳闸：假设 A 相电压为额定电压的 120% → 当 保护装置进行故障检测 → 那么 系统在 4ms 内发出 GOOSE 跳闸报文 并且 跳闸报文的重传次数为 3 次。场景 电压正常不应跳闸：假设 100% → 当 检测 → 那么 不应生成跳闸指令。

## 行文规则

> 本节「禁止」＝ 指南 §3.3.2/§3.5.8 中本文档的「约束」（写作边界）；指南中的「约束」不指 [MUST]/[SHOULD] 内容级标记。

**必须**
- Gherkin 语法规范（`# language: zh-CN` 开头；`功能/场景/假设/当/那么/并且` 关键字）
- Gherkin 关键字固定为 `功能/作为/我希望/以便/场景/假设/当/那么/并且`（多预期用「并且」）。
- 文件组织：每个功能目录**一份** `acceptance-tests.md`，所有场景写入同一文件（场景数量过多时精简描述粒度，不拆分文件）
- 场景名唯一，描述业务结果而非实现步骤；正常路径与异常路径都要有场景
- 每个场景的预期结果必须可判定，不得只写动作而无结果
- 业务规则应被验收场景完整覆盖（与 `feature_design` §处理流程/§边界约束联动）

**禁止**
- ❌ 技术实现细节或代码级验证 → 归 `unit_test`
- ❌ 功能约束定义 → 归 `feature_design`
- ❌ 模糊或不可验证的预期（如「系统正常工作」而无可判定结果）
