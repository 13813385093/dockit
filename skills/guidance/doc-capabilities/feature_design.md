# 能力说明：feature_design（feature-design.md）

> 指南：§3.3.2 / 类型 T-11（维护索引，供指南更新时同步本文件；AI 无需访问）
> 层级：Level 2（feature）· 必选 · 编写顺序第 11 · 位于 `module-<模块名>/features/<功能名>/`

## 定位

功能的完整行为规格：功能描述、触发条件、适用前提、处理流程、异常路径、边界约束（What）。开发者据此实现，测试人员据此编写测试。只定义「做什么」，不描述「怎么做」。不写实现方式（HOW，→ architecture，§函数调用关系 除外）与决策理由（→ decision_log）。

## 承载的决议主题

| 决议主题 | 落点（章节 / 新增记录） |
|---------|---------|
| 功能行为定义 / 核心逻辑 | §功能描述 |
| 功能启动的精确条件（阈值、持续时间） | §触发条件 |
| 执行前必须满足的状态 | §适用前提 |
| 核心业务步骤（有序流程） | §处理流程 |
| 非正常流程的处理方式 | §异常路径 |
| 功能级约束指标（延迟、可靠性、重试） | §边界约束 |
| 函数级静态结构 / 函数签名与调用关系 | §函数调用关系 |

## 段落结构（7 个章节，顺序固定）

### §功能描述

一段话概括功能的核心逻辑。

- 格式：一段话（单个自然段）
- 正例：当逆变器交流侧 A 相电压超过设定阈值时，系统在 4ms 内发出跳闸指令。
- 反例：做电压保护。（无触发、无指标，无法据此实现与验证）

### §触发条件

表格列出功能启动的精确条件。

- 格式：表格，列名固定为 `条件 | 阈值 | 持续时间要求`
- 正例：电压值 > 1.1 × 额定电压（持续时间 > 10ms）；电压值 < 0.9 × 额定电压（持续时间 > 10ms）。
- 反例：电压异常时触发。（阈值与时长缺失，条件不可判定）

### §适用前提

列表列出功能执行前必须满足的状态。

术语澄清：设计侧「**适用前提**」＝功能可执行时系统必须已处于的状态；测试侧 `Given 前置条件` / Gherkin `假设` ＝单个用例的初始输入状态，二者不同层次。

- 格式：列表（每条一个系统必须已处于的状态）
- 正例：设备已注册并在线；通信链路已建立；用户已通过双重身份认证。

### §处理流程

有序编号列出核心业务步骤（从触发到完成的逻辑链）。本文档描述**单个功能**的行为链；**模块/组件级流程归 `architecture.md` §关键流程**。

- 格式：有序编号列表（1. 2. 3. …）
- 正例：SV 模块接收采样值 → 保护逻辑计算电压偏差 → 判断是否超过阈值 → 生成 GOOSE 跳闸报文 → 发送至智能终端。

### §异常路径

表格列出非正常流程的处理方式。

- 格式：表格，列名固定为 `异常场景 | 处理方式 | 通知方式`
- 正例：通信超时 → 重试 3 次后告警；数据校验失败 → 丢弃并记录日志。

### §边界约束

表格列出功能级非功能性约束。编号规则：

- 格式：表格，列名固定为 `约束 ID | 约束 | 约束级别 | 目标值 | 说明`
- `[MUST]` 必须编号 `C-1xx`；`[SHOULD]` 可选编号 `S-1xx`；`[MAY]` 不编号
- ID 绑定约束条目而非内容：修改内容保留 ID，删除约束则 ID 废弃不复用
- 编号在**本文档内唯一**；跨文档引用用完整形式（语法见指南 §3.5.5）：`<doc_type>@project-charter:C-101`（顶层）／`<doc_type>@<模块名>:C-101`（模块层）／`<doc_type>@<模块名>.<功能名>:C-101`（功能层，如 `feature-design@order.order-timeout-cancel:C-101`）。
- 正例：

| 约束 ID | 约束 | 约束级别 | 目标值 | 说明 |
|---------|------|---------|-------|------|
| C-101 | 电压越限到跳闸的延迟 | [MUST] | ≤ 4ms | 保护动作时限 |
| S-101 | 报文重传次数 | [SHOULD] | = 3 | 丢包恢复 |

### §函数调用关系

表格列出本功能涉及的全部函数。

- 格式：表格，列名固定为 `函数 | 签名 | 职责 | 调用`
- 只设计函数边界（函数名 + 入参/出参签名 + 职责 + 调用链），不写函数体与实现细节。
- 签名用 `implemented_in` 声明的语言表达；未声明语言时用语言无关伪签名。
- 仅描述本功能内部的函数调用；跨组件/跨模块调用归 `architecture` / `inter_module_contract`。
- 入口函数标注「入口」；`调用` 列列出被调用函数名，无则记 `—`。

- 正例：`detectOverVoltage(samples []Sample, threshold float64) → TripCmd`（入口），调用 `evaluateThreshold`、`issueTrip`。
- 反例：写 if/else 分支、循环、变量赋值等函数体实现。

## 行文规则

> 本节「禁止」＝ 指南 §3.3.2 中本文档的「约束」（写作边界）；指南中的「约束」不指 [MUST]/[SHOULD] 内容级标记。

**必须**
- 按 §段落结构 的 7 个固定章节与各节声明的格式（表格列名 / 编号列表 / 段落）落笔，章节顺序固定、不增删
- 行为规格语言，不写实现代码
- 约束可验证：量化指标给数值（如延迟 ≤ 4ms），规则类给可判定标准
- `[MUST]` 约束必须编号且文档内唯一
- 门禁 G4 的覆盖范围 = **本文档 §边界约束 的编号 [MUST]**；顶层/模块层文档（`non_functional_constraints` / `global_policies` / `domain_model` 等）的编号约束不纳入 G4，由各自文档自行验证。每条编号 `[MUST]` 约束应被 `unit-tests.md` 的「覆盖约束」行引用——写约束时同步规划对应测试场景
- 决策结论与选型理由不在本文档落地；结论变化时在 `decision_log` 追加新记录，不改写旧记录
- 函数调用关系只写函数边界（函数名 / 签名 / 职责 / 调用），不写函数体

**禁止**
- ❌ 实现代码 / 框架调用 / 伪代码 → 源码文件
- ❌ 函数体 / 分支 / 循环 → 源码文件（函数调用关系只到函数边界）
- ❌ 跨模块 / 跨组件调用 → `architecture` / `inter_module_contract`
- ❌ 决策理由、方案对比、选型权衡 → `decision_log`（追加新记录，不改写旧记录）
- ❌ 测试用例 / 验收场景 → `unit_test` / `acceptance_test`
- ❌ 领域实体与业务不变条件定义 → `domain_model`
- ❌ 模块组件划分与实现方式（HOW）→ `architecture`（§函数调用关系 除外，见该节）
- ❌ 跨功能全局量化底线 → `non_functional_constraints`
- ❌ 模糊或不可验证的表述（如「电压异常时触发」而无阈值与时长；无来源的指标）
