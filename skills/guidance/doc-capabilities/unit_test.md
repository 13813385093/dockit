# 能力说明：unit_test（unit-tests.md）

> 指南：§3.3.2 / §3.5.6 / 类型 T-13（维护索引，供指南更新时同步本文件；AI 无需访问）
> 层级：Level 2（feature）· 必选 · 编写顺序第 13 · 位于 `module-<模块名>/features/<功能名>/`

## 定位

定义每个测试场景的输入、操作和预期输出（GWT 结构，**语言无关、纯描述性**）。开发者据此编写实际测试代码，评审者据此判断实现是否正确。关注**代码正确性**（"代码写对了吗？"）。不写业务场景（→ acceptance_test）与 mock/框架细节（→ 源码测试文件）。

## 承载的决议主题

| 决议主题 | 落点（章节 / 新增记录） |
|---------|---------|
| 单元测试用例（输入/操作/预期） | 新增 `### 测试用例：<用例名>` |

## 段落结构（记录式：每条记录含固定要素，顺序固定，条数不限）

```
### 测试用例：<用例名称>

覆盖约束: [引用的约束 ID，如 C-101；无则省略]

#### Given 前置条件
#### When 触发动作
#### Then 预期结果
```

术语澄清：设计侧「**适用前提**」＝功能可执行时系统必须已处于的状态；测试侧 `Given 前置条件` / Gherkin `假设` ＝单个用例的初始输入状态，二者不同层次。

- 格式：每条记录 = `### 测试用例：<用例名称>` 标题 + `覆盖约束` 行 + `Given 前置条件` / `When 触发动作` / `Then 预期结果` 三个 `####` 区块
- 正例：模拟电压异常场景，电压值为额定值的 120%。（Given 前置条件）
- 正例：保护装置监测到电压异常。（When 触发动作）
- 正例：系统在 4ms 内发出 GOOSE 跳闸报文；跳闸报文重传次数为 3 次。（Then 预期结果）

## 行文规则

> 本节「禁止」＝ 指南 §3.3.2/§3.5.6 中本文档的「约束」（写作边界）；指南中的「约束」不指 [MUST]/[SHOULD] 内容级标记。

**必须**
- 每条用例采用 GWT（Given-When-Then）三元组，语言无关
- 每条用例一个 `### 测试用例：<用例名称>` 记录，名称唯一，且须能对应到一个测试函数
- `覆盖约束` 行声明本用例验证的约束 ID（语法见 `feature_design` §边界约束编号规则）；**门禁 G4**：每个编号的 `[MUST]` 约束至少被一个用例引用
- `覆盖约束` 引用的是**本功能** `feature_design` §边界约束 的编号（G4 范围仅限该层）。
- 与 `feature_design` 的联动：边界约束（如 `[MUST] C-101 扫描周期 ≤ 5 分钟`）应直接体现在用例的预期结果中
- `When 触发动作` 调用函数时，函数名应引用 `feature_design` §函数调用关系 中的函数，保证「测哪个函数」有权威来源
- 预期结果必须可判定；每条用例只验证一件事

**禁止**
- ❌ 集成测试或端到端测试 → 归 `acceptance_test`
- ❌ 业务场景描述 → 归 `acceptance_test`
- ❌ mock 细节或框架调用 → 归源码测试文件（`xxx_test.go` / `xxxTest.java`）
- ❌ 模糊或不可验证的预期（如「系统正常工作」而无可判定结果）
