## 定位

精简模式单文件宪章：将 5+1 种顶层基础类型合并到一个文件（business_context / technical_framework / non_functional_constraints / global_policies 必选，inter_module_contract 推荐、stakeholders 可选）。保留完整表达深度，减少文件数量。

## 段落结构

每个 `##` 章节对应一个基础类型，内部章节与对应基础类型能力文件一致：

- ## 业务背景 → 项目动因 / 项目目标 / 目标用户 / 业务范围 / 关键术语表
- ## 技术框架 → 技术栈概览 / 架构风格 / 主要框架与中间件 / 部署模型 / 开发环境与工具链
- ## 非功能性约束 → 性能约束（含可用性可靠性）/ 安全约束（含合规标准）/ 编码规范 / 平台兼容性 / 第三方依赖约束
- ## 全局策略 → 架构模式 / 安全与认证 / 可观测性 / 数据一致性 / 异常处理 / 合规与审计 / 代码规范 / 命名约定 / 依赖管理
- ## 模块间接口契约 → 接口 / 事件 / 结构（字段级）
- ## 干系人（可选）→ 角色定义 / 信息需求矩阵

写作规则与对应基础类型能力文件相同（如 §边界约束编号规则同 `non_functional_constraints`）。

## 行文规则

**必须**
- **约束 ID 在整个文档内唯一**（跨章节不重复，因合并后是同一文档）
- `contains` frontmatter 列表与正文章节保持一致；stakeholders 可选，不在列表即视为省略
- 拆分（§3.7）时各 `##` 章节成为独立基础文档，版本初始化为 0.1.0

**禁止**
- ❌ 未拆分前在精简模式下新建独立顶层基础文档（`doc new` 会以 `new_doc.minimal_profile` 拒绝，应写入本文档对应章节）
- ❌ 违反各基础类型能力文件的写作边界（如 ## 技术框架 不写量化指标）
