# 议题（SessionSpec）类技能改进方案

> 范围：`spec-start` / `spec-load` / `spec-pause` / `spec-close` / `spec-abort` / `spec-archive`
> 依据：用户 6 条要求 + 《01-技能梳理》中的 P0–P2 问题清单
> 状态：**方案待确认**，确认后按 §6 顺序落地

---

## 1. 设计基线：从"随时落盘"改为"两个落盘点 + 单点写文档"

现状的问题不是顺序错，而是**职责重叠**：`spec-pause` 既写会议纪要又写 ProjectSpec，`spec-close` Step 5 再重复一遍同一套"决议→文档"路由，`spec-abort`/`spec-close` 又各自内联归档。

改进后建立三条基线：

| 基线 | 内容 | 解决的问题 |
|------|------|-----------|
| **B1 两个落盘点** | 讨论期间**不落盘**；只有 `spec-start`（创建议题）与 `spec-pause`（保存纪要）写 `SessionSpec/active/` | 要求 2；消除"边聊边写"的不可控 |
| **B2 ProjectSpec 单点写入** | 议题全生命周期内，**只有 `spec-close`** 写 `ProjectSpec/`；`start`/`load`/`pause`/`abort` 一律不碰 | 要求 2、4；消除 pause↔close 重复流程（P1-16） |
| **B3 议程驱动** | `pending_decisions[]` 就是议程：`start` 建立 → `load` 复述 → `pause` 推进 → `close` 结清 | 要求 1、3；让"讨论到哪了"有唯一数据源 |

对应的数据字段职责（`spec_schema.py` 已支持，无需改结构）：

| 字段 | 由谁写 | 语义 |
|------|-------|------|
| `session_spec_id` / `scenario` / `project` / `created_at` / `related_doc_types` | `spec-start`（后三个 CLI 自动填充） | 只读标识 |
| `pending_decisions[]` | start 建立议程；pause 推进 status/新增 | **议程**：`needs_discussion` → `resolved` / `deferred` / `blocked` |
| `resolutions[]` | pause（+close 的收尾）；**只增不改** | 已定决议（`detail` ≥150 字） |
| `next_steps[]` | pause（增/删） | 后续动作 |
| `status` / `closed_at` / `closed_reason` | close / abort | 终态（`closed_reason` 必填，CLI 强校验） |

## 2. 议题生命周期（改进后）

```
        spec-start：建立议程（pending_decisions）
                    │  ← 唯一"创建议题"落盘点
                    ▼
   ┌────────────► active ─────────────────────────┐
   │  讨论（不落盘）                              │
   │        │                                     │
   │   spec-load：复述议程，重开上下文续聊         │
   │        │                                     │
   │   spec-pause：全部讨论落盘为会议纪要（唯一落盘点，不写 ProjectSpec）
   │        │                                     │
   └────────┘（可反复）
                    │
        ┌───────────┴────────────┐
   spec-close                spec-abort
   ①内置 pause 落盘           ①确认原因
   ②梳理 ProjectSpec 变更清单  ②标 abandoned
   ③用户审核 → 批量写入        ③直接归档（不写任何文档）
   ④标 closed（原因必填）→ 归档
                    │
                    ▼
        closed / abandoned ──► spec-archive（兜底：中断残局才用）
```

**诚实性原则（新增）**：关闭时未解决的议程**不允许为了关闭而谎报 `resolved`**，必须显式标 `deferred`（推迟，转 `next_steps`）或 `blocked`（受阻，记录阻塞原因）。现状 `spec-close` 教的"把未解决项 status 改为 resolved 清除"是错误示范，本次修正。

## 3. 六个技能逐个改进

### 3.1 `spec-start` — 议题开启开关 + 议程落地（要求 1）

**现状**：提取 topic/scenario → 生成 id → `spec write`，`pending_decisions` 留空；结尾还做 `doc structure` 文档方向引导。

**改进后流程**：

| Step | 动作 | 变化 |
|------|------|------|
| 0 | `spec status` 确认无活跃议题 | 保留 |
| 1 | `spec schema` 取字段定义 | 保留 |
| 2 | 提取 `topic` + `scenario`（三场景） | 保留 |
| **3（新增·强制）** | **提炼本次讨论的待决议议程**：从用户描述中拆出 2–N 条候选议题，逐条给 `topic`（精确命名，作为匹配 key）+ `note`（待澄清点/背景），**与用户逐条确认**（可增/删/改/合并），确认后即为本次议题的议程 | 要求 1 核心 |
| 4 | 生成 `session_spec_id`（`{YYYYMMDD}-{topic-kebab}`，与 CLI `_generate_spec_id` 一致），提议名称等确认 | 补格式说明（P1-10） |
| 5 | 组装 spec：`pending_decisions` = Step 3 议程（`status: needs_discussion`）、`resolutions: []`、`next_steps: []` → `spec write` | 议程落盘 |
| 6 | 复述议程 + 说明落盘规则（"讨论期间不落盘，需落盘时执行 `spec-pause`"）+ 提示 `spec-pause` 是唯一保存手段 | 替换原"文档方向引导" |

- **删除**：结尾的 `doc structure` + scenario→文档层级表（该路由属于 `spec-close` 的职责，`_index.md` §2 已有权威版本）。
- **工具清单**：`spec status` / `spec schema` / `spec write`（3 条，删掉从未使用的 `spec read`、`doc structure`、`doc read`、`doc update-section`、`doc add-section`）。
- **新增异常处置**：`spec write` 报 "SessionSpec/active/ 下存在残留文件" 时，**不自行删文件**，引导用户走 `spec-archive` 兜底或人工处理。
- **边界**：`resolutions` 允许为空；若用户首轮已有明确结论，才写 `resolutions`（`detail` ≥150）。

### 3.2 `spec-load` — 重开上下文 + 复述议程（要求 3）

**现状**：只跑 `spec status` 做岔路判断，靠**中文散文子串匹配**（期望「无活跃议题」，实际文案是「没有活跃议题」）；description 与行为不符。

**改进后流程**：

| Step | 动作 |
|------|------|
| 1 | `spec status`：给用户一句话现状 |
| 2 | **路由改用 `spec read` 的 JSON 可解析性**（能解析出 JSON 即 active；输出以「错误:」开头即异常；否则无活跃议题）→ 消除散文匹配（P1-8） |
| 3 | **首屏先复述议程**（要求 3 核心）：待决议逐条列出 `topic` + `note`（这是上下文重建块），再给已决议摘要与后续计划 |
| 4 | 询问用户推进哪一条，进入讨论；若议程已清空 → 提示可 `spec-close` |

复述格式（固定，便于人快速接手）：

```
📌 议题 20260915-cert-auth ｜场景：技术评审 ｜状态：active

待决议议程（3 项）：
 ① 认证协议选型 —— needs_discussion
    待澄清：OAuth2 与自签 JWT 的取舍，及是否引入第三方 IdP
 ② token 有效期策略 —— needs_discussion
 ③ 与网关的鉴权边界 —— deferred（上次搁置）

已决议（2 项）：…
后续计划（1 项）：…

请选择要推进的议题（或直接抛出新话题，我会把它加入议程）。
```

- **修正**：description 改为「加载活跃议题并复述待决议议程，续接讨论」；正文技能名统一连字符（`spec-start` 等，P1-12）。
- **工具清单**：`spec status` / `spec read`（2 条）。
- **不做**：不检查 DevSpec、不写任何文件（保持"只读前导"定位；DevSpec 总入口问题留待 dev 模块专项）。

### 3.3 `spec-pause` — 唯一落盘点，只写会议纪要（要求 2）

**现状**：146 行里约 45 行是 ProjectSpec 写入流程（能力库加载 / `doc structure` / `doc read` / update / add / `doc new`），与 `spec-close` 重复。

**改进后流程**（瘦身为 ~60 行）：

| Step | 动作 | 变化 |
|------|------|------|
| 1 | `spec read` 取当前 spec | 保留 |
| 2 | 从**本轮对话**提取变更：新决议（含 `detail` 引导，≥150 字）/ 议程状态推进 / 新增议程 / 后续计划增删 | 保留（强化"议程推进"） |
| 3 | 展示变更清单给用户确认（含"累计待落盘决议 N 条"计数） | 改造：原清单里的"→ 计划写入 xxx.md"整列删除 |
| 4 | 组装完整 spec → `spec write`（全量替换） | 保留 |
| 5 | 复述：已保存 X 条决议、议程剩余 Y 项；**提示 ProjectSpec 尚未写入，将在 `spec-close` 时统一落盘** | 新增（补齐认知差） |

- **明确删除**：所有 `doc *` 命令与能力库加载流程 → 迁往 `spec-close`。
- **工具清单**：`spec read` / `spec schema` / `spec write`（3 条）。
- **边界新增**：不改变 `status`；不写 `ProjectSpec/`（哪怕用户明确要求"顺手把文档改了吧"→ 引导到 `spec-close`，或先记录为决议）。
- **description**：「保存本次讨论到会议纪要（唯一落盘点），不写 ProjectSpec、不改状态」。

### 3.4 `spec-close` — 落盘 → 清单 → 审核 → 写入 → 归档（要求 4）

**改进后成为议题类最重的技能**，五步：

| Step | 动作 | 说明 |
|------|------|------|
| 1 | **执行 `spec-pause` 的核心流程**（内联，不跨技能引用） | 提取本轮变更 → 组装 spec → `spec write`；确保上下文全部进纪要（要求 4 前半） |
| 2 | **议程结清检查**：未 `resolved` 的议程逐条与用户确认 → 标 `resolved`（已解决）/ `deferred`（推迟，写入 `next_steps`）/ `blocked`（受阻，记原因）；**禁止谎报 resolved** | 新增 |
| 3 | **梳理 ProjectSpec 变更清单**：`doc structure` → 按 `_index.md` §2/§3 路由每条决议 → 读能力文件取段落结构与行文规则 → `doc read` 目标文档 → 判定动作（`update-section` / `add-section` / `doc new`），产出**清单表**交用户审核（可改/删/合并/标记"不落文档"） | 要求 4 中段；能力库流程在此集中 |
| 4 | **审核通过后批量写入**：`doc new` 先行（否则无目标文档），再 update/add；逐条记录结果，末尾汇总"成功 N 条 / 失败 M 条（含错误码与建议）"，失败项交用户决定重试或人工处理 | 要求 4 后段 |
| 5 | **标终态并归档**：`spec write`（`status: closed`、`closed_at`、`closed_reason` **必填**）→ `spec archive` | 要求 4 结尾 |

清单表模板（Step 3 产出、Step 4 执行）：

| # | 决议 topic | 目标文档 | 章节 | 动作 | 写入摘要 |
|---|-----------|---------|------|------|---------|
| 1 | 认证协议选型 | `technical-framework.md` | §主要框架与中间件 | update-section | … |
| 2 | 退款功能设计 | `module-pay/features/pay-refund/feature-design.md` | —（新建） | doc new | … |
| 3 | 内部讨论口径 | —— | —— | 不落文档 | 仅会议纪要，理由：… |

- **新增纪律**：① 每条决议必须有归宿（写入某文档，或显式标"不落文档"+理由），不允许静默漏写；② 写入前必须用户审核通过（不得边梳理边写）；③ `closed_reason` 缺失时先问用户，不编造。
- **工具清单**：`spec read` / `spec schema` / `spec write` / `doc structure` / `doc read` / `doc new`（含 `--author`）/ `doc update-section` / `doc add-section` / `spec archive`（9 条）。**移除** `doc remove-section`（删除段落属人工或后续议题范畴，收紧误用面；如需保留请告知）。
- **修正**：删除"MCP 标记为 closed"旧术语（P1-9）；`doc new` 补 `--author` 说明（P1-14）；命令示例一律用字面量引用（不用 `<...>` 占位符，避免 P0-6 类误用）。

### 3.5 `spec-abort` — 作废即归档（要求 5）

**改进后**：Step 1 确认意图 + **原因必填**（`closed_reason` 由 CLI 强校验）→ Step 2 `spec read` → Step 3 标 `abandoned` / `closed_at` / `closed_reason` → Step 4 `spec write` + `spec archive`（**直接归档，不写任何 ProjectSpec 文档**）。

- **新增引导分支**：若用户其实想保留讨论成果 → 引导改用 `spec-close`（避免把有价值的讨论一键作废）。
- **新增明确边界**：作废不产生任何文档副作用（与 `spec-dev-loop` 的 abort 语义一致）。
- **工具清单**：`spec read` / `spec write` / `spec archive`（3 条；删掉从未在步骤中使用的 `spec status`）。

### 3.6 `spec-archive` — 降级为兜底技能（要求 6）

**定位改写**：「归档兜底。正常归档由 `spec-close` / `spec-abort` 在流程末尾内联完成，本技能**通常不由用户或议程直接调用**，只在流程中断、`active/` 出现残局时使用。」

**新增"残局体检"能力**（这是它唯一的存在价值）：

| 残局 | 识别方式 | 处置 |
|------|---------|------|
| 已终态但未归档（上次 close/abort 中断在最后一步） | `spec status` 报「有已关闭/已作废但未归档的议题」 | 直接 `spec archive` |
| 仍是 `active` 却想清理 | `spec status` 报「当前有活跃议题」 | 引导 `spec-close` / `spec-abort`，**不代为改状态** |
| 无活跃议题但 `active/` 有残留文件 | `spec write` / `spec status` 报「存在残留文件」/「多个活跃」 | 交人工判断（CLI 按串行约束主动拒绝，不自动处理） |

- **工具清单**：`spec status` / `spec archive`（2 条）。
- **说明归档语义**：`SessionSpec/active/<sid>.spec.json` → `SessionSpec/archive/`，不可逆；归档后如需再议必须新开议题。

## 5. 配套改动（文本与 CLI）

**SKILL.md 前言"输出约定"统一替换为**（5 个技能一致）：

> 输出约定：`spec status` / `spec read` / `spec schema` 直接输出文本——`spec status` 是一行中文状态描述，`spec read` 是议题 JSON（无活跃议题时输出中文提示），`spec schema` 是字段定义 JSON；三者失败时以「错误:」开头。其余命令输出 JSON 信封，含 `success` / `message` / `data` / `suggestions` 字段，退出码 0 = 成功、1 = 失败。未指定 `--root` 时 CLI 从当前目录向上自动查找项目根；`--root` 是全局参数，必须写在命令组（`spec`/`doc`/`dev`）之前。

**建议的 CLI 侧小改（可与本模块并行，非阻塞）**：

- **S1**：`spec_schema.py` 中 `session_spec_id` 的 `description` 由 `'ss-tech-ref-module-A-001'` 改为 `'{YYYYMMDD}-{topic-kebab}'`，例 `'20260618-cert-auth'`（3 行，消除 P1-10 误导源）。
- **S2**：`spec status --json` 输出 `{success, data:{session_spec_id, status, ...}}`，让路由彻底脱离中文散文（为 §3.2/§3.6 的长期稳定）；技能侧写成"优先用 `--json`，不可用时回退文本判断"。
- **S3**：`spec write` 在 `status=closed` 且存在未 `resolved` 的 `pending_decisions` 时返回 warning，把 §3.4 Step 2 的纪律下沉为机器护栏。

## 6. 风险与缓解

| 风险 | 说明 | 缓解 |
|------|------|------|
| **未 pause 的讨论会丢** | 讨论期间不落盘，上下文只在会话里；用户直接关窗口/超长截断则本轮讨论丢失 | ① `spec-start` Step 6 与 `spec-load` 结尾都明确提示"需要保存时说一句，我执行 `spec-pause`"；② AI 在对话明显变长或用户出现收尾语气时**主动提醒** pause；③ 这是本次设计的既定取舍（用户要求 2） |
| **长期不 close 导致 ProjectSpec 滞后** | 决议只在 SessionSpec，项目文档看不到 | `spec-pause` 输出"累计待落盘决议 N 条"计数，让滞后可见 |
| **close 变重、单次审核负担大** | 所有文档写入集中在 close | 清单表 + 逐条可勾选（用户可只批部分条目，未批项记入 `next_steps`） |
| **归档不可逆** | `active → archive` 无回退；`closed/abandoned` 为终态 | 保留 `spec-abort` 的二次确认；`spec-close` Step 5 归档前展示最终纪要摘要 |

### 8.3 走查中额外发现并修复的 CLI 缺陷（S0）

**`spec status` 在 `SessionSpec/archive/` 尚未创建时误报「当前无活跃议题」。**

- 触发条件：项目初始化后**第一次** `spec status` 调用发生在创建议题之后（旧实现把"archive/ 不存在"直接当作"项目刚初始化"返回）。
- 危害：状态行与 `spec read` 的 JSON 结果自相矛盾，会让 AI 误判岔路——`spec-start` Step 0 会以为无议题而重复创建（随后被 `spec write` 的残留检测拒绝），`spec-load` Step 1 会向用户谎报现状。
- 修复：先建目录，再走正常的状态判定，仅"确实无议题"时保留「已初始化」话术。
- 回归：`tests/test_session_flow.py::TestStatusRouting` 覆盖（修复前该用例失败）。
