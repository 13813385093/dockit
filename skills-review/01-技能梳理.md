# 技能梳理报告（评审第一步）

> 范围：`skills/` 全部资产（9 个 SKILL.md + 能力库 + CLI 脚本）
> 方法：逐份通读 SKILL.md → 对照 `skills/scripts/cli.py` 实现 → 在临时项目（`/tmp/dkprobe`，由 `init_project()` 真初始化）实测每条关键指令
> 结论标注：**【实测】**= 已跑命令复现；**【静态】**= 代码/文本对照得出

---

## 一、技能资产全景（四层）

```
① 技能层   skills/spec-*/SKILL.md           9 个技能（面向 AI 的行为规范）
② 能力库层 skills/guidance/doc-capabilities/  _index.md + 15 个 doc_type 能力文件
③ 工具层   skills/scripts/*.py                CLI 实现（cli.py 2026 行 + 4 个支撑模块）
④ 数据层   SessionSpec/ ProjectSpec/ DevSpec/ ReviewSpec/（技能只经 CLI 读写）
```

| 层 | 部署路径 | 部署方式 | 消费者 |
|----|---------|---------|--------|
| 技能层 | agent 的 skills 目录（如 `~/.reasonix/skills/`） | `doc-kit install-skills <dir>` | AI Agent |
| 技能层副本 | `<项目根>/.doc-kit/skills/spec-*/` | `init_project()` → `copy_skills()` | 人工搬运参考 |
| 能力库 | `<项目根>/.doc-kit/skills/guidance/doc-capabilities/` | `copy_guidance()` | AI 写文档前必读 |
| 工具层 | `<项目根>/.doc-kit/cli/` | `copy_cli()` | AI + 人工 |
| 模板 | `<项目根>/.doc-kit/templates/` | `copy_templates()` | `doc new` |

关键设计特征：**技能不携带数据，只携带纪律与流程**；一切读写都收敛到项目内固定的 `<项目根>/.doc-kit/cli/cli.py`。9 份 SKILL.md 共享同一段"最高优先级"前言（CLI 独占读写 + 能力库例外 + 前置条件 + 工具清单 + 输出约定）。

## 二、九个技能逐个梳理

### 2.1 议题（SessionSpec）主线：5 个

| 技能 | 定位 | 触发时机 | 状态迁移 | 命令数(实用/声明) | 产出 |
|------|------|---------|---------|------------------|------|
| `spec-load` | 每次对话的**前导动作**，看当前在哪 | 新对话开始 | 不变 | 3 / 8 | 状态判断 + 岔路指引 |
| `spec-start` | `idle` 状态的**唯一岔路** | 用户提需求且无活跃议题 | 无 → `active` | 4 / 8 | `SessionSpec/active/<sid>.spec.json` |
| `spec-pause` | 保存进度，**不改状态** | 用户说"就到这里/先保存" | `active`（不变） | 6 / 9 | spec 决议/待定/计划 + 文档段落写入 |
| `spec-close` | 正常结束议题 | 用户说"讨论完了/关闭" | `active` → `closed` → 归档 | 8 / 10 | 闭合 spec + 文档写入 + 移入 archive |
| `spec-abort` | 非正常终止议题 | 用户说"算了/作废" | `active` → `abandoned` → 归档 | 3 / 4 | 作废 spec + 归档（**不写文档**） |
| `spec-archive` | 补归档已 closed/abandoned 的议题 | 用户说"归档/清理" | `closed`/`abandoned` → 归档 | 2 / 3 | 目录搬迁 |

- **决议不可变**是主线硬约束：`resolutions` 只能新增（修正需另开议题）；`pending_decisions` 只能新增或改 `resolved`；`next_steps` 可增可删。
- `spec-pause` Step 3 与 `spec-close` Step 5 是**同一套"决议 → 文档"路由流程**（`doc structure` → 读 `_index.md` 定位 doc_type → 读能力文件 → `doc read` → `update-section`/`add-section`/`doc new` → 用户确认 → 写入）。
- 写入时序纪律：`spec write` 先落盘会议纪要，再写 ProjectSpec（"纪要先安全"）。

### 2.2 开发执行（DevSpec）主线：1 个

`spec-dev-loop`（386 行，最重的技能）——把 ProjectSpec 的设计翻译成代码派生制品。

| 阶段 | 内容 | CLI 命令 | 状态机 |
|------|------|---------|--------|
| Phase 0 | 入口：断点检测 + 分支检查 | `dev status` | — |
| Phase 1 | 规划（人机交互）：读范围文档 → 代码考古 → 约束整合 → 任务提案 → 用户确认 → 建分支 | `dev plan create/read/update-section`、`dev task set` | — |
| Phase 2 | 任务循环 LOOP | `dev task update/annotate`、`dev notes append` | `pending→in-progress→implemented→unit-green→done`，失败 `→fixing→in-progress` |
| Phase 3 | 功能对齐（验收测试 + G4 约束覆盖 + 回归） | `dev align`、`dev report-write` | `tasks-done→aligned` |
| Phase 4 | 模块集成（G3 契约闭合 + CodeNotes 整理） | `dev integrate`、`dev report-write` | `features-done→integrated→documented→done` |
| Phase 5 | 收尾（提示人工合并分支 + 归档） | `dev close/abort`、`dev archive` | — |

核心纪律四条（本技能独有）：
1. **ProjectSpec 全程只读**（不可协商）——设计问题只记 `CodeNotes`/报告，改设计留给循环外的人工/会议流程；
2. **DevSpec 读写一律经 CLI**，`plan.md` 是循环内的唯一工作上下文；
3. **分支隔离**：`dev-loop/<sid>` 与开发循环一一对应，合并回主干是**人工**动作；
4. **自测必须真实运行**（禁写 trivial 测试糊弄，反"假绿"）。

### 2.3 独立任务式（不经议题）：2 个

| 技能 | 定位 | 前置 | 关键动作 | 产出 |
|------|------|------|---------|------|
| `spec-smart-git` | 按标签（feat/fix/docs/refactor/chore）分解待提交变更，生成多个语义独立提交 | git 仓库 | 收集 → 提案（人确认，支持 merge/edit/skip/assign）→ 逐个提交 → 可选 push | N 个规范化 commit |
| `spec-code-review` | 从 git 变更出发比对设计文档，记录差异 | git 仓库 + 评审锚点 | 取锚点 → `git log/diff`（默认排除纯文档）→ AI 标注热点 → 用户圈范围 → 并排比对定性 → 更新锚点 | `ReviewSpec/code-review-<ts>.md` |

`spec-code-review` 的差异三分类是人主导的：**A 设计变更 / B 实现偏差 / C 误报**；报告必填段落由 CLI 校验（`# ` 标题、`## 基本信息`、`## 评审热点`，缺失只 warning 不阻断）。

### 2.4 能力库层（技能的知识支撑）

`_index.md` 三级路由，是"决议 → 目标文档 → 章节"的唯一向导：

1. §1 文档类型总览：**15 种**（顶层 7 / 模块层 4 / 功能层 4，按 `level: top|module|feature` 落盘）
2. §2 议题场景 → 候选 doc_type（`spec-scribe` / `tech-ref` / `feature-dev` 三场景，与 `spec_schema.py:SCENARIO_DOC_TYPES` 一一对应）
3. §3 决议主题 → 目标文档 → 典型章节
4. §4 新增 vs 更新判断 + 工具表

每个能力文件统一四段式：**定位 / 承载的决议主题 / 段落结构（含正反例）/ 行文规则与禁止**。这套"写前须知"质量高，是本仓库最扎实的部分。

## 三、调用关系与状态机

```
                        ┌──────────── spec-load（前导）────────────┐
                        │                                          │
   idle ──spec-start──► active ──┬──spec-pause──► active（循环）    │
                                 ├──spec-close──► closed ──┐        │
                                 └──spec-abort──► abandoned ┴─► archive
                                                            ▲
                                             spec-archive ───┘（补归档）

   dev 轨（独立串行）：spec-dev-loop ══► spec-smart-git（任务 done / 功能对齐时提交）
                                          └► spec-code-review（循环外评审，允许改文档）

   review 轨：spec-code-review（锚点增量，独立于议题）
```

**边界分工（技能自述）**：`spec-dev-loop` 只读 ProjectSpec、只提交到 `dev-loop/<sid>`；`spec-code-review` 在循环**外**做文档一致性评审、允许改文档；`spec-smart-git` 只做提交不做评审。三者对 git 的边界声明一致（git 一律走 `bash`，CLI 不执行 git）。

**两条串行约束**：一个活跃议题、一个活跃开发循环（CLI 检测到多个直接报错）。

## 四、问题清单（按严重度分级）

### P0 — 照 SKILL.md 原样执行会直接失败【全部实测复现】

| # | 位置 | 问题 | 实测结果 |
|---|------|------|---------|
| 1 | `spec-dev-loop` Phase 1 Step 3.5 | 指令 `dev plan update-section 'plan.md#2.5 代码风格快照'`，但 `PLAN_SKELETON` 只有 §1–§6，**没有 §2.5** | `ERROR [dev_plan.section_not_found] 未找到段落: plan.md#2.5 代码风格快照` |
| 2 | `spec-dev-loop` Phase 2 Step 1→3 | 步骤里**没有 `implemented` 环节**，Step 3 直接从 `in-progress` 跳 `unit-green`；而 CLI 状态机要求 `in-progress→implemented→unit-green` | `ERROR [dev_task.invalid_transition] 状态 in-progress → unit-green 不合法` |
| 3 | `spec-dev-loop` Phase 2「任务超时与重试」 | 要求每张任务卡必含 `timeout_seconds`/`retry_count`/`retry_delay`，但 `TASK_ALLOWED_KEYS` 不含这三项，`dev task set` **静默丢弃**（不报错，最危险） | 写入后 `tasks.json` 实测无这三个键 |
| 4 | 同上 | 超时/失败态 `timed_out`、`failed` 不在 `DEV_TASK_STATUSES`；"continue `<task_id>` / skip `<task_id>`"无对应 CLI | `ERROR [dev_task.invalid_status] status 'timed_out' 不合法` |
| 5 | `spec-smart-git` Step 1-0、`spec-code-review` Step 1-0 | 用 Windows 写法 `git --version >nul 2>&1`，在 bash 下会**生成名为 `nul` 的文件** | 实测 cwd 出现 `nul`（19 字节） |
| 6 | `spec-dev-loop` Phase 1 Step 4 | 指令写成 `'<plan.md>#2. 约束整合'`，尖括号占位符易被当成字面量 | `ERROR [dev_plan.invalid_ref] reference 必须指向 plan.md，收到 '<plan.md>'` |

> 1–4 属**功能设计缺陷**（技能描述了 CLI 不存在的能力，需二选一：补齐 CLI 或改技能）；5–6 属**表述缺陷**（改动小、影响直接）。

### P1 — 契约与一致性问题【静态对照】

| # | 位置 | 问题 |
|---|------|------|
| 7 | 9 份前言「输出约定」 | `spec read` / `spec schema` 返回的是**裸 JSON**（无 `success`/`message`/`data`/`suggestions` 外壳），与"JSON 结果含这四个字段"的约定不符；且 `spec read` 在无活跃议题时返回中文散文（`当前没有活跃议题…`），不符合"以「错误:」开头即失败"的判定规则 |
| 8 | `spec-load`/`spec-start`/`spec-archive` | 靠**中文散文子串匹配** `spec status` 输出（技能期望「无活跃议题」，实际文案是「没有活跃议题」）。CLI 文案一变，路由即失效；`spec status` 未提供机器可读字段 |
| 9 | `spec-close` §成功后 | 残留旧架构术语："**MCP** 标记为 closed"（CLI 已取代 MCP，其余 8 份均已改口径） |

| 11 | `spec-load` frontmatter | description="加载之前的会议记录，继续讨论"，正文定位却是"每次新对话的第一步（看状态）"；实际也不加载历史记录（仅 `status`，无 `read`） |
| 12 | `spec-load`/`spec-archive` 正文 | 交叉引用写作 `spec_start` / `spec_pause` / `spec_close`（下划线），与实际技能名（连字符）不一致，跨技能引用可能落空 |
| 13 | `_index.md` §唯一权威源 | 模板路径写作 `src/app/templates/<文件名>`（开发态源码路径），项目内实际位于 `.doc-kit/templates/`；同文件 §4.2 又写 `.doc-kit/templates/`，自相矛盾 |

| 15 | `spec-dev-loop` Phase 2 Step 4 | 引用"指南 §3.3.3 原则"，但**指南不随 init 部署到项目**（`copy_guidance()` 只拷 `doc-capabilities/`），对 AI 是悬空引用 |

### P2 — 结构与可维护性【静态对照】

| # | 问题 | 证据/影响 |
|---|------|----------|
| 17 | **前言 9 份重复且已漂移** | 9 个前言块 MD5 全不相同；差异集中在工具清单与「纯文本输出」枚举。改一条全局纪律要动 9 个文件 |
| 18 | **工具清单过度声明** | `spec-load` 声明 8 条命令、步骤中只用 3 条；`spec-archive` 声明 3 用 2；未用的命令（如 `doc remove-section`、`spec write`）增加 AI 误用面 |
| 19 | **归档路径三重冗余** | `spec-close` Step 7 与 `spec-abort` Step 4 各自内含 `spec archive`，`spec-archive` 技能又独立存在；三处语义重叠 |
| 20 | **命名体系语义拥挤** | `spec-` 前缀同时覆盖 SessionSpec（start/pause/close/abort/archive/load）、DevSpec（dev-loop）、ReviewSpec（code-review）三类对象，前缀已不传达对象信息 |
| 21 | **缺少两个入口技能** | ① 无初始化技能（"项目必须已由 doc-kit 初始化"是硬前置，AI 无法自举，只能终止）；② 无总路由技能——`spec-load` 只覆盖 SessionSpec，不检查 DevSpec（`dev status`）与 ReviewSpec 锚点，活跃开发循环中的对话没有统一入口 |
| 22 | **纪律表述存在张力** | dev-loop 前言同时给出"任何文件读写一律经 CLI"与"CLI 连续失败 2 次可降级直接只读 tasks.json"；且 Step 3.5 用 `bash`+`find|xargs cat` 读源码。豁免边界（ProjectSpec 文档 vs 源码 vs DevSpec）散落各处，未集中定义 |

### 已具备的护栏（值得保留）

- `tests/check_doc_consistency.py`：注册表 / 模板 / 能力库 / _index / 指南 五者不漂移。

## 五、下一步建议（供评审决策）

1. **先定 P0 的处置方向**（每项二选一，需产品决策）：
   - #1：`PLAN_SKELETON` 增补 `## 2.5 代码风格快照`（推荐，与技能 Step 3.5 对齐）／或技能改用 `add-section`。
   - #2：技能步骤补 `implemented` 环节（推荐）／或放宽状态机。
   - #3/#4：CLI 支持 `timeout_seconds`/`retry_count`/`retry_delay` 字段与 `timed_out` 态（**推荐**，超时重试是真实开发需求）／或从技能中删除该章节。
   - #5/#6：纯表述修正，直接改。
2. **抽出共享前言**：把 CLI 纪律/前置条件/工具约定收敛为 1 份 `skills/_shared/preamble.md`（或由 init 时装配），消除 9 份漂移。
3. **给状态输出加机器可读字段**：`spec status` / `dev status` 增加 JSON 模式，技能改按 `data` 字段路由，去掉中文字符串匹配。
4. **补两个入口技能**：`doc-kit-init`（或明确写清"由人工/GUI 初始化"的终止话术）与总路由（合并 load + dev status 检查）。

6. **技能功能裁剪评审**（第二步主线）：重点议 `spec-archive` 是否保留、`spec-load` 是否升级为总路由、`spec-pause`/`spec-close` 的重复流程是否合并为共享能力库文件。
