## 1. 成立的部分（其中一条比你的理由更硬）

### 1.1 文档体系确实已经具备"编码落地"的输入——这是设想的地基

已核实：`feature-design.md §函数调用关系`（函数边界 + 签名 + 调用关系 + 入口标注）、`unit-tests.md`（GWT + 「覆盖约束」行）、frontmatter `implemented_in`（`{path, lang}`）都已存在。能力库甚至明确写着 §函数调用关系 是「行为规格到代码实现的桥（弥补『设计 → 编码』的最后一步）」。

结论：**dev-loop 不是在"设计代码"，而是在"翻译+验证"已定文档**。你的骨架化，恰好是把"文档编译成接口"这一步显式化。地基是实的。

### 1.2 骨架阶段真正珍贵的价值：把"设计偏差的发现点"前移（比省上下文更重要）

这是你的设想里**最有价值但你自己没点明**的一点，我把它算作主收益：

- 现状技能允许"轻/中偏差"**在实现阶段就地吸收**（Phase 2 Step 4：轻 → 采用当下合理方式；中 → 选择当下更合理者实现，记 CodeNotes 就好）。这条规则与"文档是唯一权威源"存在张力：偏差被吸收在代码里，文档却不动。
- 骨架化把发现点从"实现后"提前到"写第一行代码前"。成本对比很直白：
  - 骨架阶段发现签名不对 → 改 1 个签名 + 通报，没有代码要返工；
  - 实现阶段发现 → 改 N 个方法 + 已写测试 + 已提交历史。
- 而且骨架阶段的产物是**用户可见、可评审的接口清单**——这让"设计变更走议题、不在循环内消化"这条纪律第一次真正可执行（现状只能靠自觉）。

**所以：即使上下文收益打折（见 §3.3），这个设想的骨架阶段也该做。**

### 1.3 拓扑序 + 骨架 ⇒ 逐方法验收在机制上自洽

现状已要求任务按拓扑序（"先被调用者、后调用者"）。配上骨架后产生一个好性质：**每验收一个被调用方法，它的调用方立刻变得可冒烟**——可验证性随进度单调递增。这让"逐方法验收"不是硬凑的流程，而是有序的。

---

## 2. 需修正 ①：派发粒度不该是"一方法一子代理"

**你的原话**："逐一实现方法……调用子代理做方法实现"。方向对，粒度偏细。三个具体问题：

1. **简报开销可能超过实现本身。** 一个 5 行的 `evaluateThreshold`，其简报（签名 + 能力注释 + 约束 ID + 调用关系 + 风格快照 + 禁止事项）常常比实现更长。方法越小，派发越亏。
2. **同文件并行会互相打架。** 如果你的类方法都在同一个文件（很正常），多个子代理并行编辑同一文件会冲突，只能串行 → 并行收益归零，只剩开销。
3. **微观设计决策会外溢。** 骨架冻结了*签名*，但没有冻结*内部约定*：中间数据结构、错误如何向上传递、日志粒度、边界值归一化。紧耦合的调用链（入口+助手）本该共享这些决策；拆到独立上下文里，每个子代理各造一套，主代理最后还得做"缝合"。这恰好是"少占上下文"的反面——缝合成本又回到主上下文。

**建议规则（可直接写进技能）**：

> 派发单元 = **一个文件内的一个内聚调用链**（而非一个方法）。
> 可并行 ⟺ 各单元的落点文件互不相同。
> 验收仍可逐方法进行（`accepted` 的判据是方法级的），**派发粒度与验收粒度解耦**。

——即：你对"逐方法"的直觉在**验收**上是对的，在**派发**上是错的。这两个粒度不该绑在一起。

## 3. 需修正 ②③④

### 3.1 ② "签名与调用逻辑已确定"是假设，不是保证

你说："因为这一步之前已经将方法签名做好，相互的调用逻辑也确定了"——这是把子代理模式立在一个**经验假设**上。现实中写函数体时经常发现：签名少了一个参数、返回值不够表达、助手函数根本不必要、或者两个方法该合并。

**没有出口的冻结签名会两头坏**：子代理要么为了守签名写出别扭代码，要么悄悄违反（验收只看签名就查不出语义偏移）。

**需要补一份"签名变更协议"**：

| 情形 | 处置 |
|------|------|
| 实现中发现签名/调用关系需调整 | **不允许就地改**；先 `dev task update <id> --status blocked --note '签名需变更：<理由>'` |
| 影响面 = 本任务的私有助手 | 主代理确认后改骨架 + 更新 tasks.json 的 `signature`/`calls` + 记 CodeNotes（轻） |
| 影响面 = 入口签名 / 跨任务调用关系 / 契约 | 升级用户；若涉及跨模块契约 → 回议题（中/重），循环内只记录 |
| 变更后 | 之前已 `accepted` 的调用方任务需重新走验收（骨架基线变了） |

同时给验收一个**可检测的基线**：`tasks.json` 里的 `signature` 就是骨架基线，验收第 1 项比对它——签名漂移无法静默通过。

### 3.2 ③ 上下文收益被高估：省的是"写"，不是"看"

诚实的账：

| 流向 | 派发前 | 派发后 |
|------|--------|--------|
| 读设计文档 | 主上下文 | 主上下文（不变） |
| 写实现代码 | 主上下文（**大**） | 子代理上下文（**省下来了**） |
| 验收（读 diff / 跑测试 / 比对签名） | —— | **回流主上下文**（新成本） |
| 失败重派（带证据） | —— | 再次回流 |
| 简报组装 ×N | —— | 主上下文（小但非零） |

结论：**省下的是"作者的上下文"，不是"审阅的上下文"**。而且总 token 是**增加**的（同样的信息在 N 份简报里重复）。真正的收益是"主代理能在长循环里保持清醒"，不是省钱。

由此推出两条设计要求：
- **验收要"机械优先"**：编译状态、`git diff --stat` 文件清单、签名比对（grep/AST）、约束 ID 是否出现、子代理留下的临时冒烟脚本——这些都让回流上下文**小**。
- **验收深度按风险分层**：普通纯函数走机械验收；带 IO/事务/并发/缓存的方法（现有 `// NEGATIVE:` 纪律已在标记它们）才回读代码做语义判断。**一律回读代码 = 派发白做；一律不回读 = 验收是走过场。**

### 3.3 ④ "所有方法都交给子代理"是过度统一

子代理质量有方差，N 个子代理 = N 次引入劣质补丁的机会。合理做法是混合：

| 方法类型 | 实现者 | 理由 |
|---------|--------|------|
| 机械、模板化、重复度高（getter、映射、校验、样板） | **子代理** | 隔离收益最大、风险最低 |
| 高风险（IO/事务/锁/缓存/并发、跨模块契约触点） | **主代理亲自** | 语义验收成本高于实现成本，派发反而更贵 |
| 内聚调用链 | 同一单元（子代理或主代理整包） | 见 §2 |

技能里应写成"**默认派发，高风险可回收自做**"，而不是"必须派发"。

## 4. 缺口 ⑤⑥

### 4.1 ⑤ 验收测试与回归在设想里缺席

你的 Step 4 只提"单元测试"。但功能是否"做完"的判据是 `dev align`，而它的依据是 `acceptance-tests.md` 的 Gherkin 场景 + 回归范围（依赖它的下游）。**单元测试全绿 ≠ 功能对齐。**

必须保留（现状技能有，别丢）：Phase 3 的验收测试执行（自动化为主、人工证据兜底）、G4 约束覆盖检查、依赖反查的回归。你设想的"测试"应明确分两层：**单元测试（GWT，翻译 unit-tests.md）** 与 **验收测试（Gherkin，翻译 acceptance-tests.md）**，后者是 `dev align` 的前置。

### 4.2 ⑥ 横切/基础设施类工作无归属

你的模型里，工作只有两种：feature（日常）与 module（我建议的契约/集成专项）。但现实里还有第三类：**跨 feature / 无 feature 归属的横切工作**——构建脚本、共享工具库、依赖升级、数据库迁移框架、CI 流水线。

这类工作既不是某个 feature 的功能行为，也不是模块契约闭合。当前设想没有它的出口，结果会是"塞进最近的 feature"或"绕过 dev-loop 直接改代码"。

需要你明确一个出口（三选一）：走 spec 议题 + 人工实现 + `spec-code-review` 复核 ／ 新增第四种 scope（`chore`，轻量流程）／ 明确声明"这类工作不走 dev-loop"。

## 5. 一个反直觉的补充：feature scope 本身并不省上下文

你给"一次只做一个 feature"的理由是"避免一次性任务太多，上下文被大量占用"。但**真正的上下文控制器是"骨架 + 派发 + plan.md 作为唯一工作上下文"，不是 scope**：

- 一个大 feature 可以有 30 个方法，一样撑爆上下文；
- 一个小 feature 只有 3 个方法，收窄 scope 几乎没收益。

feature scope 的真实价值在别处，而且是真价值：**完成判据明确**（`dev align` 有唯一的对齐对象）、**验收范围可界定**、**回归影响面可反查**。建议把这条理由写进技能——理由写对了，规则才不会被误用（比如用它去挡本该一次做完的事）。

---

## 6. 需补规则 ⑦：右尺寸（避免新流程官僚化）

新流程的固定开销：骨架 + 用户确认 + N 份简报 + 6 项验收 ×N + 测试。对一个"§函数调用关系只有 2-3 个方法、且在同一文件"的小功能，这套开销可能超过开发本身——**流程一旦明显不划算，人就会绕开它**（这与你最初"让 skills 更合理好用"的目标相悖）。

**建议右尺寸规则**：

> 当本功能 §函数调用关系 的方法数 ≤ 3 且落点在同一文件时：Phase 2 与 Phase 3 合并（骨架可只写在 plan.md 摘要，不必落源码 stub），保留"用户确认接口"与"主代理验收"两个闸门，但豁免逐方法派发与逐项验收清单。

## 8. 一句话回答"我的想法是否合理"

**合理，而且你抓到了两个真问题**（设计文档没被真正"编译"进代码、主代理被实现细节淹没）。
但有三个地方我把你的想法往回收了一格：**派发粒度太细**（该按内聚单元，不按方法）、**签名冻结是假设**（要配变更协议，否则会僵化或被悄悄违反）、**上下文收益没你想的大**（省的是写、不是看，验收必然回流）。
另外补两个你漏掉的：**验收测试与回归不能丢**（它们才是"功能做完"的判据），**横切工作没有出口**。
把这些补上，这套"骨架化 + 委托实现"是比现状明显更好的流程——**主要不是因为省上下文，而是因为它把设计偏差的发现点从代码里挪到了代码前**。
